## Коротко

Два дефекта, которые не видны при чтении кода и не видны при запуске отдельного набора.

**Первый: CI не работал.** Четыре последних прогона на `main` — `failure`, включая `6f1c000`. Набор `e2e_new_features_test` входил админом под демо-пароль, а у админа с коммита `f48b2bd` пароль отдельный. Падение на пятом наборе из девяти останавливало цикл (`set -e`), и **14 наборов из 18 не запускались вообще** — включая все восемь самодостаточных, регрессы на деньги и удаление данных.

**Второй: признак «онлайн» не вычислялся нигде.** Функция `user_online` лежала в двух копиях, и обе возвращали `False` на каждом вызове: считали aware минус naive и `fromisoformat` по объекту `datetime`, а исключение глоталось `except Exception: return False`. Данные при этом были верные — админка показывала 4 онлайн-человека, пока API отдавал `false` всем.

**Третий: вторая группа наборов не могла запуститься вообще.** Восемь из девяти наборов поднимают приложение через `fastapi.testclient`, которому нужен `httpx`, а `httpx` не объявлен ни в одном файле зависимостей — он просто лежал в рабочей venv. Группа была подключена, но не выполнялась ни разу, потому что её останавливал первый дефект. Как только первый починили, она упала на входе.

**Четвёртый: кэш списка задач отдавал мусор.** `GET /tasks/` без фильтров кладёт в Redis результат `query.all()`, то есть ORM-объекты, через `json.dumps(..., default=str)`. Первый запрос отдаёт нормальный список, все последующие в течение минуты — `["<app.models.Task object at 0x...>"]`. В `docker-compose.yml` и `docker-compose.prod.yml` Redis задан, так что путь живой; не замечалось потому, что фронт ходит с `?page=`, а такой запрос некешируемый, и потому, что локально Redis не запущен.

**Пятый: заказы товаров не проверялись ничем.** В `app/api/products.py` лежит весь жизненный цикл заказа товара с деньгами — 15 роутов, включая выплату продавцу и возврат покупателю. В CI на это не было ни одной проверки: слово `order` не встречалось ни в одном файле `tests/`. Все уже сделанные там защиты можно было откатить молча. Добавлен набор на 52 проверки.

**Шестой: страница «Мои задания» не работала вообще.** `GET /tasks/my` строил запрос с `joinedload(Task.executor)`, а у модели `Task` нет ни одного `relationship()` — только колонки `customer_id` и `executor_id`. Обращение к несуществующему атрибуту падало с `AttributeError` **на построении запроса**, ещё до обращения к базе, то есть роут отдавал 500 на любой запрос при любых данных. Фронт ходит именно сюда (`MyTasksPage.jsx:49`, `tasksStore.js:70`). Ни один набор его не вызывал — наткнулся я на это случайно, когда писал регресс на сериализацию enum.

**Седьмой: правка импорта может потеряться молча.** Заменяя 23 копии выражения на общий `enum_value`, я отправил несколько правок одного и того же файла одним заходом — и в двух файлах из восьми правку импорта затёрло. `compileall` такое пропускает (имя не разрешается при компиляции), наборы не ловят (`NameError` вылезает только на том запросе, который имя задел, а `/wallet/transactions` до этого не вызывал никто). В CI добавлен шаг `ruff F821` — он находит это за секунду и без базы.

**Восьмой: приватное вложение из чата читал любой.** Вложение в переписке — это `file_url` вида `/files/<id>`, то есть **ссылка, а не файл**. При отправке сообщения это поле приходит от клиента, схема проверяла только форму строки, а подпись `file_url_with_token` считается от одного лишь id файла — без пользователя, без сделки, без срока. Поэтому участник любой своей сделки мог назвать id чужого приватного вложения, получить на него валидную подпись и прочитать файл, **хотя доступ к самой переписке, где файл лежит, ему закрыт 403**. Проверено живьём: 200 и 358 байт чужого файла. Закрыто проверкой владельца при отправке и выдачей подписи только на файлы, видимые участникам сделки.

Все восемь исправлены и закрыты регрессами. Плюс закрыто слепое пятно в проверке документации и найдено несколько вещей, которые решает пользователь, а не я.

## Дефекты

### D1. Критический. Вход админом под демо-паролем — CI стоял, 14 наборов не запускались

`tests/e2e_new_features_test.py:195` брал пароль админа так:

```python
admin_pwd = os.environ.get("DEMO_PASSWORD", "")
```

Но `seed_demo.py:61` заводит админу **отдельный** пароль:

```python
ADMIN_PASSWORD = os.environ.get("ADMIN_PASSWORD") or generate_strong_password()
```

`ADMIN_PASSWORD` не задан ни в `ci.yml`, ни в `docker-compose`, ни в `render.yaml`, ни в bat-файлах — то есть админ всегда получает сгенерированный пароль. Демо-пароль на нём не работает никогда.

Последствия различались по окружению:

- **в CI** (`DEMO_PASSWORD=ci-demo-password`) — вход 401, проверка `Арбитр admin@delo.ru доступен (seed)` падает, `set -e` в цикле `Run test suites` останавливает шаг. Наборы 6–9 группы, все 8 самодостаточных и проверка смены пароля админа не выполняются;
- **локально** (`DEMO_PASSWORD` не задан) — набор печатал `SKIP Арбитр`, пропускал весь блок арбитража и заканчивался зелёным `31 passed, 0 failed`.

Доказательства:

```
цикл CI с set -e, окружение джобы:
  test_auth_flow                         ок
  security/check_refresh_token_whitelist ок
  test_csrf_coverage                     ок
  test_chat_reviews_notifications        ок
  e2e_new_features_test                  УПАЛ (код 1)   ← здесь цикл встаёт
  РЕЗУЛЬТАТ: 31 passed, 1 failed
  (наборы 6–9 группы, 8 самодостаточных и смена пароля админа не запускались)

API GitHub Actions, последние прогоны main:
  6f1c000  failure
  707b782  failure
  839dfe2  failure
  a5fecc4  failure
```

Исправлено в `528dc75`. В `tests/_helpers.py` появился общий резолвер `demo_password()` / `admin_password()`: берёт значение из окружения, иначе из `backend/demo_password.txt` — того же файла, куда его пишет seed. `SKIP` заменён на честный `FAIL` с объяснением: набор, который пропускает половину проверок и отчитывается зелёным, хуже отсутствующего.

**Почему это важно не только как «починили CI».** Второй симптом (тихий SKIP) объясняет, почему прошлая итерация отчиталась «0 ошибок»: набор запускался без `DEMO_PASSWORD`, блок арбитража пропускался, и ноль был получен по неверной причине. Ровно та же ловушка, что и в прошлый раз с пятью незапущенными наборами.

### D3. Высокий. Признак «онлайн» возвращал `false` всегда — в двух копиях

Функция `user_online` существовала в двух местах и в обоих была сломана одинаково — глушением исключения:

```python
# app/api/users.py:83
return (datetime.now(timezone.utc) - last_seen_dt).total_seconds() < 120
#   → TypeError: can't subtract offset-naive and offset-aware datetimes
#     (колонка last_seen объявлена Column(DateTime) без timezone=True)

# app/api/responses.py:15
return (datetime.utcnow() - datetime.fromisoformat(user.last_seen)).total_seconds() < 120
#   → TypeError: fromisoformat: argument must be str
#     (user.last_seen — объект datetime, а не строка)
```

Оба `TypeError` ловились `except Exception: return False`, поэтому снаружи всё выглядело как «пользователи офлайн».

Замер на живом стенде до правки:

```
igor.last_seen      = 2026-09-20 07:07:36.311384 (тип: datetime)
отставание от сейчас: 91.5 сек — внутри окна 120 с
users.user_online     -> False
responses.user_online -> False
эталон (admin.py:64, SQL):  online-пользователей: 4
```

Что это ломало: `online` в `GET /users/me`, `online` в `GET /specialists/`, `specialist_online` в списке откликов и бейдж «Онлайн» в `SpecialistsPage.jsx:137` — он не отрисовывался никогда. При этом `last_seen` честно обновляется middleware `track_last_seen` (`main.py:203`), то есть данные были верные, а признак на них врал.

Исправлено в `d472ae1`:

- `app/core/presence.py` — одна реализация на проект, сравнивает naive UTC с naive UTC (как `admin.py`), принимает `str` (след миграции `b31957f1dbe9`), naive и aware `datetime`, `None`. Исключения не глушит;
- `admin.py` берёт окно из `ONLINE_WINDOW_SECONDS`, а не из литерала `120` — иначе счётчик и бейджи разъедутся;
- `main.py` пишет в `last_seen` naive UTC. Прежде туда уходил aware `datetime.now(timezone.utc)`; значение совпадало с UTC только потому, что смещение нулевое, а замена на `datetime.now()` уехала бы на три часа и держала бы всех «онлайн» ещё три часа после ухода;
- `tests/security/check_online_status.py` — регресс на 17 проверок: сама функция и четыре поверхности, где признак виден снаружи. Добавлен в CI.

Регресс проверен **в обе стороны**:

```
исправленный код:                       passed=17 failed=0  (код 0)
дефект внесён обратно:                  passed=7  failed=14 (код 1)
  FAIL свежий naive datetime -> онлайн | исключение TypeError: can't subtract offset-naive and offset-aware datetimes
  FAIL GET /users/me (свежий): HTTP 200 | пришло 500 Internal Server Error
  FAIL GET /specialists/: HTTP 200 | пришло 500 Internal Server Error
```

### D6. Критический. Кэш списка задач отдавал мусор вместо задач

Нашлось попутно, когда я проверял, не оставит ли CI красным живой Redis в джобе. Оказалось, дело не в тестах.

`GET /tasks/` без фильтров кэшируется в Redis на 60 секунд. В кэш уходил результат `query.all()`, то есть ORM-объекты `Task`, а сериализация была такая (`app/api/tasks.py:139`):

```python
cache.set(cache_key, json.dumps(result, default=str), ttl_seconds=60)
```

`default=str` вызывается для всего, что JSON не умеет, — и превращает каждый `Task` в строку `str(obj)`. Замер на живом Redis:

```
1-й запрос (промах кэша), HTTP 200
   тело: [{"title":"ПОКРАСИТЬ ЗАБОР","budget":5000,"id":1,"status":"open", ...}]

2-й запрос (попадание в кэш), HTTP 200
   тело: ["<app.models.Task object at 0x000001B81163A850>"]

сырое значение в Redis:
   ["<app.models.Task object at 0x000001B81163A850>"]
```

### D9. Низкий, латентный. Пустое enum-поле уезжало в JSON строкой `"None"`

Попутно, при написании D8. По коду разбросано **23 копии** одного выражения:

```python
"category": product.category.value if hasattr(product.category, "value") else str(product.category)
```

Выглядит защитным, но при пустой колонке `hasattr(None, "value")` ложно, и `str(None)` даёт **строку** `"None"`. В JSON уезжает категория с названием `None`, а не `null`, и фронт не совпадает ни с одним фильтром — при том что в базе всё в порядке.

Замер до правки:

```
category='None' condition='new'
```

Две копии оказались в одном файле: `_serialize_product` (список, «мои товары») и `get_product_detail`, который **не использует** `_serialize_product`, а дублирует его inline. То есть «починить в одном месте» тут не сработало бы — я на этом и споткнулся: правка `_serialize_product` не изменила ответ детали товара.

Добавлен `app/core/enums.py::enum_value` — одна реализация вместо копий, по той же причине, что и `app/core/presence.py` для D3. Применён в обоих местах `products.py`. Стало `category=None`.

Дефект латентный: `ProductCreate` задаёт `category` и `condition` по умолчанию, seed тоже, поэтому через API пустых строк не появляется. Но обе колонки объявлены `nullable`, а строку может создать миграция, админский скрипт или ручная правка.

Сначала были заменены только две копии в `products.py`. Остальные 21 — теперь тоже.

**Почему я всё-таки доделал.** Первая редакция этого отчёта говорила «поля всегда заполнены, дефект латентный». Это неверно. `nullable=False` не выставлен **ни у одной** из этих колонок — в SQLAlchemy `Column()` по умолчанию `nullable=True`, — а у двух колонок нет вообще никакого `default`:

```python
# app/models/__init__.py:101
type = Column(SqlaEnum(TransactionType))
# app/models/__init__.py:379
category = Column(SqlaEnum(ProductCategory), index=True)
```

То есть NULL в них разрешён схемой и приезжает оттуда, где строку создают напрямую: миграция, админский скрипт, импорт, ручная правка. Замер на живом приложении это подтверждает — `"category":"None"`, `"role":"None"`, `"type":"None"`, `"status":"None"` в ответах, притом что в базе честный NULL.

Заодно выяснилось, зачем это важно на практике. Фронт сравнивает роль строго — `role === 'customer'`, `role === 'specialist'` (`MyTasksPage.jsx:95,158,161`, `tasksStore.js:70`, `ProfilePage.jsx:513`). Строка `"None"` не совпадает ни с одним из них, как и `null`, но, в отличие от `null`, она truthy: ветка «роль есть» рисует пользователю слово None. В CSV-выгрузке кошелька (`users.py:378`) `"None"` уезжал в колонку «Тип» вместо пустой ячейки.

Заменено во всех восьми файлах. Регресс — `tests/security/check_enum_null_serialization.py`, 49 проверок. Обнуляет колонки **прямым SQL**: через ORM нельзя, `default` подставляется ровно тогда, когда атрибут не задан, поэтому `Task(category=None)` сохранит `other`, а не NULL. Отдельный раздел проверяет, что в базе действительно NULL — иначе набор был бы зелёным и на сломанном коде.

Побочно: `auth.py` кладёт `role` в payload access-токена, и этот claim **не читает никто** — ни бэкенд (`is_admin` смотрит email из `ADMIN_EMAILS`, а не токен), ни фронт (он берёт `data.role` из тела ответа). Claim мёртвый; оставлен как есть, чтобы не менять формат токена в этом заходе.

### D11. Критический. Приватное вложение из чата читал любой пользователь

Задача была «проверить все места, куда вкладываются фото, кроме профиля». Вложений три вида: фото задания (`Task.images`), фото товара (`Product.images`) и вложение в переписке (`Message.file_url`). Плюс аватар и портфолио — это профиль, его не трогал.

Дефект нашёлся в переписке.

**Устройство.** Вложение — это **ссылка, а не файл**:

```
POST /upload/image?scope=private  →  {"url": "/files/7", "file_id": 7}
POST /tasks/{id}/messages         ←  {"file_url": "/files/7"}
```

`file_url` приходит **от клиента**. Схема `MessageCreate` проверяла только форму строки — `^/files/\d+(\?[^\s]*)?$` или http(s) — и всё. Ни существования файла, ни владельца, ни того, что этот файл вообще относится к этой сделке.

Дальше ссылка хранится как есть, а подпись выдаётся при отдаче, потому что браузер не прикладывает `Authorization` к запросу картинки из `<img>`. И вот тут корень:

```python
# app/core/security.py
def sign_file_token(file_id: int) -> str:
    return "f1" + hmac.new(SECRET_KEY, f"file:{file_id}".encode(), sha256).hexdigest()
```

Подпись — **чистая функция от id файла**. Ни пользователя, ни сделки, ни срока в ней нет. Значит, «получить подпись» и «иметь право на файл» — разные вещи, а выдавалась подпись кому угодно, кто назвал id.

**Как это выглядит в атаке.** Три шага, ни одного взлома:

1. участник своей сделки отправляет в свой же чат сообщение с `file_url = "/files/1"` (чужой файл);
2. сервер сохраняет и в ответе подписывает: `"/files/1?token=f19f4ddc..."`;
3. `GET /files/1?token=...` → **200, 358 байт чужого файла**.

При этом сам доступ к переписке, где этот файл лежит, у атакующего закрыт — `GET /tasks/{чужой}/messages` отдаёт 403. То есть проверка доступа к переписке обходится: подпись запрашивается не там, где файл лежит, а в своей переписке.

Доказательство до правки:

```
  OK   чужая переписка закрыта                          | http=403
  OK   приватный файл без подписи закрыт                | http=403
  FAIL чужой файл прикрепить нельзя                     | http=200 (ожидалось 403)
  FAIL ссылки на чужого файла в переписке нет           | file_url='/files/1?token=f19f4ddc...'
  FAIL чужой файл по такой ссылке не отдаётся           | http=200, 358 байт — ФАЙЛ УТЁК
=== ИТОГ: passed=11 failed=4 ===
```

Комментарий в коде рядом с этим местом утверждал, что утечки быть не может: «подпись выдаётся здесь, а не запрашивается клиентом, — значит, получить её может только участник сделки». Логика верная ровно наполовину: участник сделки — да, **любой участник любой своей сделки** — и это не то же самое, что «тот, кому виден файл».

**Что это за файлы.** `/upload/file?scope=private` кладёт в переписку не только картинки: сметы, договоры, сканы. Через `/upload/image?scope=private` — фото объекта, в том числе личные. Утечка не косметическая.

**Правка.** Две проверки, потому что одного рубежа мало — в базе уже лежат строки, попавшие туда до правки.

При отправке — прикрепить можно только **свой** файл:

```python
def _require_own_attachment(db, url, user_id):
    file_id = _attachment_file_id(url)
    if file_id is None:
        return url                       # внешняя ссылка — не наш файл, прав не даёт
    stored = db.query(StoredFile).filter(StoredFile.id == file_id).first()
    if not stored:
        raise HTTPException(400, "Файл не найден — загрузите его через POST /upload/image")
    if stored.owner_id != user_id:
        raise HTTPException(403, "Прикрепить можно только свой файл")
    return f"/files/{stored.id}"         # каноническая ссылка, чужой query отброшен
```

При отдаче — подпись только на файл, видимый участникам **этой** сделки:

```python
participants = {task.customer_id, task.executor_id} - {None}
for row in db.query(StoredFile).filter(StoredFile.id.in_(ids)).all():
    if not row.is_private or row.owner_id in participants:
        visible.add(row.id)
```

Невидимому файлу подпись не выдаётся, но и сообщение не ломается — возвращается `/files/<id>` без токена, и такой запрос корректно отдаёт 403. Строки, попавшие в базу до правки, обезврежены вторым рубежом: регресс пишет такую строку **напрямую в базу, минуя API**, и проверяет, что подписи на неё нет.

Число запросов не выросло: видимые файлы собираются одним `IN (...)` на весь список сообщений, а не по запросу на сообщение.

Регресс `tests/security/check_private_attachment_access.py` — 15 проверок, пять блоков: утечка, закрытость чужой переписки, отказ прикрепить чужой файл, унаследованная строка в базе, и **законный сценарий целиком** (автор видит свою ссылку с подписью и открывает файл; участник прикрепляет свой файл и открывает его). Последний блок не декоративный: правка, которая просто ломает вложения всем, тоже прошла бы первые четыре.

Проверено в обе стороны: 15/0; с откаченной правкой — 11/4, код 1, и в выводе то самое `http=200, 358 байт — ФАЙЛ УТЁК`.

**Остальные поверхности с фото — проверены, дефекта нет.** Задача была про все места, поэтому перечисляю, что именно обошёл и почему там чисто.

**Что рядом, но я не тронул — решает пользователь.** Валидаторы `_validate_images` у `TaskCreate` и `ProductCreate` (две копии) проверяют только «JSON-массив строк с ограничением длины» — ни схемы, ни префикса `/files/`. Значит, в публичную карточку задания можно положить `https://evil.example/track.gif`, и он будет тянуться из браузера **каждого** посетителя. ## Найдено, но не правил — решает пользователь

### O1. Средний. Подсистема Celery — мёртвый код

`app/core/celery_app.py` (расписания beat), `app/tasks/email.py` и `app/tasks/cleanup.py` — **11 задач**, включая `cleanup_orphaned_files` и `check_expired_pro_subscriptions`. Есть инструкция `docs/CELERY_REDIS_SETUP.md` на 10 блоков, `redis` в зависимостях, `docker-compose.infra.yml`.

При этом воркер **не поднимает ни один контур**: `celery` нет ни в `ecosystem.config.cjs`, ни в `docker-compose*.yml`, ни в `render.yaml`. Ничто в рантайме не импортирует `celery_app` — то есть 11 задач не выполняются никем, а `docs/CELERY_REDIS_SETUP.md` описывает то, чего в развёртывании нет.

Отдельно: `check_pro_expiry.py` в своём docstring **уже опирается** на этот факт («celery нет в requirements.txt и ни один контур развёртывания не поднимает воркер») — то есть `is_pro_active` считается по сроку именно потому, что задача снятия флага не запускается. Это осознанное решение, но оно держится на неработающей подсистеме.

Решить: поднять воркер в одном из контуров — или удалить подсистему и инструкцию, чтобы не обещать того, чего нет.

### O2. Низкий. Базовая линия CSS глушит семь мёртвых классов

Охранник `check-css-classes.mjs` находит классы в разметке, которых нет в бандле. Он зелёный: `все 8264 классов из className есть в бандле (известных пропусков: 7)`. Но семь пропусков — не «старый долг в CSS страниц товаров», как написано в комментарии CI, а живые мёртвые классы:

- **шесть классов анимации** — `animate-in`, `fade-in`, `slide-in-from-right`, `slide-in-from-bottom`, `slide-in-from-bottom-4`, `zoom-in-95`. Это утилиты плагина Tailwind Animate (`tailwindcss-animate` / `tw-animate-css`), которого нет ни в `package.json`, ни в `index.css`. Значит, анимации появления не работают: выезжающая панель фильтров (`MobileFilterDrawer.jsx:56`), выезжающие чаты (`ChatsDrawer.jsx:41`), выпадающий список городов (`CityInput.jsx:284`), карточка на карте (`TaskMap.jsx:474`) появляются мгновенно, без движения;
- **`order-date`** (`MyOrdersPage.jsx:147`) — не утилита Tailwind, а обычный класс проекта, и правила для него нет нигде. При этом у всех соседей правила есть: `.order-card`, `.order-header`, `.order-info`, `.order-meta`, `.order-id`, `.order-status`, `.order-image`, `.order-details`, `.order-actions` — все в `MyOrdersPage.css`.

Это ровно тот класс дефекта, ради которого охранник и написан (прозрачные уведомления из-за пропавшего `glass`). Разница в том, что тогда его нашёл пользователь по скриншоту, а сейчас он найден — и внесён в базовую линию через `--update`.

Решить: поставить `tw-animate-css` и добавить `@import` — или убрать мёртвые классы из разметки. Трогать визуальный слой и добавлять зависимость без спроса не стал.

## Что осталось непроверенным

- **CI на последних коммитах — подтверждён, включая этот заход.** Прогоны 41 (`f9ad01c`), 42 (`bc3287c`), 43 (`37605ec`), 44 (`afd08b7`), 45 (`305e811`) и 46 (`de8686f`) — `success`, все шесть джоб. До этого 37, 38, 39, 40 были `failure`. На прогоне 42 шаг `Run self-contained regression suites` прошёл **впервые** — именно он и был красным из-за D5. На прогоне 44 отработали оба новых шага: `Lint undefined names` и двенадцатый набор группы 2. На прогоне 46 — тринадцатый, `check_private_attachment_access`, уже на **PostgreSQL с живым Redis**, то есть в окружении, отличном от моего локального SQLite.
- **Push.** Ушёл не сразу: `git credential.helper` = `helper-selector` виснет (код 124), а прямой `git-credential-wincred` отдаёт учётку `aacopov-debug` без прав на репозиторий (403). Через несколько попыток селектор ответил и все коммиты ушли. Если повторится — причина в этом, а не в репозитории.
- **Локальное окружение ≠ CI.** Проверка примеров из документации у меня сначала упала не из-за кода, а из-за отсутствующего `celery` в venv: в CI он приезжает из `requirements.txt`, а у меня набор был неполным. Лечится `pip install -r backend/requirements-dev.txt`. Это тот же класс, что D5 с `httpx`: «у меня работает» ничего не значит, если окружение собрано не по объявленным зависимостям.
- **Ограничение по фоновым процессам.** Сервер, запущенный отдельным вызовом, не доживает до следующего: фоновые процессы гасятся вместе с завершением вызова. Прогон группы 1 приходится делать одной командой — поднять сервер, дождаться, прогнать, погасить. Первая попытка дала 401 во всех наборах именно поэтому.
- **PostgreSQL.** Локальный Postgres 18 запущен, но пароль не подобран, прогон шёл на SQLite. SQLite уже маскировал дефекты в этом проекте (три дефекта миграций из комментария в `ci.yml`). Джоба `migrations` и прогон на PG проверяются только в CI.
- **Redis как настоящий сервер.** Все проверки кэша шли против `fakeredis.TcpFakeServer` — он говорит по RESP и `cache.enabled` от него действительно становится `True`, но это не боевой Redis. Поведение кэша в CI (живой `redis:7`) не проверялось ни разу, потому что группа не запускалась.
- **Браузерные джобы.** `password-form` требует Playwright и живой Vite — локально не поднимал. `agent-browser` на Windows не поддерживается.
- **`login-throttle`** проверен локально вручную (6/6), но с лимитером в памяти процесса: Redis недоступен, а в CI он есть.
- **Конкурентность.** Все защиты «атомарным UPDATE» (двойная выплата, захват остатка, двойное списание) проверены последовательными запросами. Настоящей гонки двух одновременных запросов не было ни в одном наборе — ни в новых, ни в прежних. Это отдельная работа с потоками и общей базой.

## Ловушки, съевшие время

**Чужой сервер на порту.** Первый прогон группы 1 дал 401 на демо-аккаунтах в четырёх наборах, и это выглядело как дефект авторизации. Причина оказалась в окружении: **на порту 8000 висел сервер из прошлой сессии**, со старой базой и старым паролем. Мой `uvicorn` не поднялся — в логе `[Errno 10048] error while attempting to bind`, — а тесты всё это время ходили в чужой процесс. Проверка «сервер отвечает на `/csrf-token`» этого не ловит: чужой сервер отвечает тоже.

Правило: перед прогоном убедиться, что порт свободен, а после запуска — что поднялся именно твой процесс, а не остался чужой.

**Параллельные правки одного файла.** Вторая ловушка, и она дороже. Отправив несколько правок одного и того же файла одним заходом, я получил классическую потерю обновлений: каждая правка читала исходную версию файла и записывала свой результат, поэтому уцелела только последняя. Внешне всё выглядело благополучно — каждая правка рапортовала об успехе, `compileall` молчал. Файлы, где было по четыре правки, потеряли по три; в двух из них потерялся как раз импорт `enum_value`, из-за чего четыре роута падали с `NameError` уже на живом запросе, а не на сборке.

Правило: правки одного файла — строго по одной за вызов. Разные файлы в одном заходе безопасны. Именно этот случай и стал причиной появления шага `ruff --select F821` в CI.

**Комментарий, объясняющий, почему утечки быть не может.** Третья ловушка — уже не про инструменты. Рядом с выдачей подписи в `chat.py` стоял разбор на восемь строк: подпись выдаётся сервером, а не запрашивается клиентом, «значит, получить её может только участник сделки». Читается убедительно, и именно поэтому я проскочил мимо при первом чтении файла: рассуждение подкупает тем, что оно подробное.

Ошибка в нём одна, но решающая: «участник сделки» и «тот, кому виден файл» — не одно и то же. Участник **своей** сделки может быть никем в той, где лежит файл.

Правило: комментарий, который объясняет, почему дефекта нет, — это гипотеза, а не доказательство. Доказательство — запрос, который пробует дефект и получает отказ. Если комментарий длиннее двух строк и объясняет безопасность, это сигнал написать проверку, а не поверить.
