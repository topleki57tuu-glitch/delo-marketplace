# Обновление приложения на сервере

Актуально на 01.11.2026. Сервер `213.21.229.145`, сайт `https://дело.online`
(punycode `xn--d1acsm.online`), каталог `/opt/delo-marketplace`.

---

## Коротко: как выпустить обновление

Два шага. Первый — у себя на Windows, второй — на сервере.

**1. У себя: закоммитить и запушить**

Папка проекта лежит внутри каталога сессии WorkBuddy AI
(`C:\Users\armen\WorkBuddy AI\<дата-время>\delo-marketplace`), поэтому путь
меняется от сессии к сессии. Проще открыть в этой папке терминал и выполнить:

```bash
git add .
git commit -m "что изменил"
git push origin main
```

**2. На сервере: применить**

Заходишь по SSH (или двойным кликом `server-shell.bat`) и выполняешь:

```bash
cd /opt/delo-marketplace
bash scripts/vps_update.sh
```

Всё. Скрипт сам снимет копию базы, подтянет код, прогонит миграции,
пересоберёт образы и перезапустит стек. Если новая версия не соберётся или не
запустится — сам вернёт прежнюю. Не понравилась уже работающая —
`bash scripts/vps_update.sh --rollback` (раздел «Откат обновления»).

### То же самое, но мышкой

Двойной клик по `deploy.bat` в папке проекта на Windows. Он делает ровно
шаг 2 по SSH: проверяет, что путь на сервере существует, запускает
`vps_update.sh`, потом проверяет `https://xn--d1acsm.online/health`.

> `deploy.bat` **не делает** `git push`. Если ты не запушил изменения,
> на сервере обновится старая версия, и скрипт честно напишет
> `Код не изменился (XXXXXXX)`.

Откат — двойной клик по `rollback.bat`: покажет текущую версию и ту, на
которую вернётся, и спросит подтверждение.

## Как понять, что ты в SSH, а не в Windows

Это главная ловушка. Если путать — команды выполняются на твоём компьютере,
а не на сервере, и ничего не работает.

| | Windows cmd | SSH на сервере |
|---|---|---|
| Приглашение | `C:\Users\armen>` | `root@noisy-amethyst:~#` |
| Каталог | `C:\opt\delo-marketplace` | `/opt/delo-marketplace` |
| `apt-get` | «не является внутренней командой» | работает |
| `bash` | просит WSL | работает |

**Правило: если приглашение начинается с `C:\` — ты в Windows.**

Зашёл по ошибке — выйди: набери `exit`.

## Что именно делает `vps_update.sh`

По порядку — и что будет, если шаг не удался:

| Шаг | Что происходит | Если не удалось |
|---|---|---|
| 1 | Копия базы с меткой `pre-update-<версия>` (раздел «Резервные копии») | обновление отменяется, ничего не тронуто |
| 2 | `git fetch` + `git reset --hard` — встаёт на новую версию | — |
| 3 | Проверка `.env` — дописывает только **отсутствующие** переменные | — |
| 4 | `docker compose build` — собирает образы backend/frontend | код возвращается |
| 5 | `up -d postgres` + ожидание `pg_isready` (до 2 минут) | код возвращается |
| 6 | `alembic upgrade head` — накатывает миграции БД | код возвращается, миграции откатываются (PostgreSQL применяет их одной транзакцией) |
| 7 | `up -d` + ожидание ответа `/health` (до 2 минут) | возвращается прежняя версия |
| 8 | Запись в журнал обновлений, `docker image prune`, проверка HTTPS | — |

До шага 7 контейнеры не перезапускаются: если упала сборка или миграции, сайт
всё это время работает на прежней версии.

Пока скрипт работает, ночная копия ждёт его окончания, а мониторинг не шлёт
уведомлений: перезапуск — не сбой. Два обновления сразу (`deploy.bat` и SSH)
не запустятся — второе ответит `обновление уже идёт`.

Если файлы проекта на сервере правились вручную, `reset --hard` их заменит.
Скрипт предупредит и сохранит правки в `/var/lib/delo/local-changes-*.patch`.

**Существующий `.env` не перезаписывается.** Токены, пароли и домен остаются
на месте. Это отличие от `vps_deploy.sh` — тот для первой установки и `.env`
создаёт.

### Зачем отдельный скрипт, а не `git pull && up -d --build`

Потому что при новой миграции такая связка **ломается молча**: код
пересобирается, а схема БД остаётся старой. Приложение падает на отсутствующей
колонке. `vps_update.sh` вызывает alembic всегда — даже если миграций нет,
это ничего не стоит.

## Проверка после обновления

В конце скрипт печатает что-то вроде:

```
==========================================
 Готово: https://xn--d1acsm.online — отвечает по HTTPS
 Версия: 769a261 что изменил
 Откат:  bash scripts/vps_update.sh --rollback   (вернёт 3c657e1)
```

Убедись, что `Версия` — это тот коммит, который ты запушил. Если скрипт
написал `Код не изменился`, значит, в GitHub нет новых изменений — не запушил.

Дополнительно, из Windows — двойной клик по `status-server.bat`. Он покажет
коды ответов `/`, `/health`, `/tasks/`, `/products/`, состояние контейнеров,
занятое место на диске и итог проверок мониторинга (сертификат, копии).

Или вручную:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://xn--d1acsm.online/
curl -s https://xn--d1acsm.online/health
```

Ожидаемо: `200` и `{"status":"ok"}`.

## Откат обновления

Обновление прошло, а на сайте что-то не так — вернуть версию, которая работала
до него:

```bash
cd /opt/delo-marketplace
bash scripts/vps_update.sh --rollback
```

Или двойной клик по `rollback.bat`. Скрипт покажет текущую версию и ту, на
которую вернётся, спросит подтверждение и пройдёт те же шаги, что при
обновлении: копия базы, сборка, проверка. Повторный `--rollback` вернёт
обратно.

| Задача | Команда |
|---|---|
| Вернуть предыдущую рабочую версию | `bash scripts/vps_update.sh --rollback` |
| Журнал: когда, какая версия, удачно ли | `bash scripts/vps_update.sh --history` |
| Перейти на любую версию | `bash scripts/vps_update.sh 769a261` — хеш из `--history` или GitHub |

Без команды, сам, скрипт откатывает так:

| Что случилось | Что делает скрипт | Сайт |
|---|---|---|
| Не снялась копия базы | отменяет обновление | не затронут |
| Не собрались образы, не поднялся postgres, не прошли миграции | возвращает код и образы | работает на прежней версии без перерыва |
| Новая версия не запустилась | возвращает прежнюю: из `deploy.bat` — сразу, в SSH — спросит (Enter — да) | недоступен несколько минут |

В последнем случае скрипт всё равно завершится ошибкой и напишет
`Обновление НЕ удалось`: сайт работает, но на прежней версии.

**Схема базы при откате не понижается.** Если новая версия добавила миграцию,
прежняя запустится на новой схеме. Обычно это работает: миграции добавляют
таблицы и колонки, а старый код их просто не замечает. Если прежняя версия не
поднялась или работает с ошибками, верни базу на момент перед обновлением —
скрипт сам напишет точную команду, вида:

```bash
bash scripts/restore.sh 2026-11-02_143012-pre-update-3c657e1 --db-only
```

Всё, что пользователи сделали после этой копии (задания, сообщения, оплаты),
при этом пропадёт. Поэтому сначала — откат кода, а база — только если без
неё никак.

## Если что-то пошло не так

### `backend не поднялся`

Скрипт покажет последние 50 строк логов и вернёт прежнюю версию (раздел
«Откат обновления»). Чтобы понять, почему новая не поднялась, смотри эти логи,
но сначала ответь на два вопроса:

1. Не забыл ли `git push`? Ведь на сервер приезжает только то, что в GitHub.
2. Не добавил ли новые переменные в `.env.example`, но не в `.env`?

Переменная, которой нет в окружении, читается как пустая строка и **не роняет
старт** — она просто молча отключает функцию. Так было с ЮMoney и `REDIRECT_URI`.

### Долгая сборка после смены базового образа

Если в обновлении менялся `backend/Dockerfile` или `bot/Dockerfile` — например
версия `FROM python:...` — пересборка идёт **с нуля**: слои старой базы не
переиспользуются, pip ставит все зависимости заново. Это может занять заметно
дольше обычного, и `docker compose build` при этом молчит.

Диск на сервере — 9.76 ГБ, и в момент сборки на нём лежат **обе** базовые
образы. Проверь место заранее:

```bash
df -h /
```

Если свободного места меньше ~2 ГБ — сначала `docker system prune -af`,
потом `bash scripts/vps_update.sh`. В конце скрипт сам делает
`docker image prune -f`, так что старый базовый образ после успешного
обновления не останется.

### `postgres не поднялся`

Обычно кончилось место на диске (его 9.76 ГБ):

```bash
df -h /
docker system prune -af
```

`prune -af` удалит **все** неиспользуемые образы. Если стек уже собран и
работает — это безопасно, но следующая сборка будет дольше.

### Скрипт упал на середине

Он идемпотентный — просто запусти его ещё раз. Повторный `build` переиспользует
слои, `alembic upgrade head` на актуальной схеме ничего не делает.

Вернуться на прежнюю версию — `bash scripts/vps_update.sh --rollback` (раздел
«Откат обновления»). `git reset --hard` руками не нужен: скрипт сам догрузит
нужную версию, снимет копию базы и запишет откат в журнал.

`обновление уже идёт (в другом окне?)` — значит, предыдущий запуск ещё
работает. Дождись его.

### `_domain: unbound variable` или похожее

Старая версия скрипта (исправлено в `3dde4d0`). Лечится обновлением самого
скрипта:

```bash
cd /opt/delo-marketplace
git fetch origin main && git reset --hard origin/main
```

## Резервные копии

Включить — один раз, на сервере:

```bash
cd /opt/delo-marketplace
bash scripts/backup.sh --install
```

После этого:

- каждую ночь в 00:30 (время сервера, московское) делается копия: база,
  загруженные файлы (фото, документы) и `.env`;
- каждые 5 минут работает мониторинг (раздел «Мониторинг и уведомления»);
- первая копия делается сразу — видно, что всё работает.

Копия проверяется **настоящим восстановлением**: дамп разворачивается во
временную базу рядом с рабочей, сверяются таблицы и число строк, временная
база удаляется. Копия, не прошедшая проверку, копией не считается — её не
видят ни восстановление, ни мониторинг. Ночная копия не получилась — придёт
уведомление в Telegram (если уведомления подключены).

Копии лежат в `/var/backups/delo/`, по каталогу на копию: `2026-11-02_003000`.
Обычные хранятся 7 дней, но две последние — всегда. Копии с меткой
(`pre-update-…` — перед обновлением, `pre-restore` — перед восстановлением) —
пять последних. Если места на диске не хватает, новая копия сначала удаляет
самые старые.

| Задача | Команда |
|---|---|
| Сделать копию сейчас | `bash scripts/backup.sh` |
| Список копий | `bash scripts/backup.sh --list` |
| Проверить копию ещё раз | `bash scripts/backup.sh --verify ИМЯ` |
| Журнал ночных копий | `tail -n 50 /var/log/delo-backup.log` |

### Копии вне сервера

Копии выше лежат на том же сервере: от неудачного обновления и случайного
удаления они спасают, от потери сервера — нет. Сбой у хостера, взлом,
неоплата — и копии пропадут вместе с сайтом. Поэтому каждую полную копию —
ночную и сделанную вручную — стоит сразу отправлять в облачное хранилище
**другого** провайдера. Это делает `scripts/offsite.sh`; настроить — один раз.

- Копия шифруется ещё на сервере (AES-256, ключ — из фразы шифрования).
  Хранилище получает только шифр: ни провайдер, ни тот, кто узнает ключ от
  бакета, копию не прочитают.
- В хранилище копии лежат 30 дней, три последние — всегда.
- Выгрузка не удалась — придёт уведомление в Telegram (если уведомления
  подключены, раздел «Мониторинг и уведомления»).
- Копии с меткой (перед обновлением, перед восстановлением) остаются только
  на сервере.

Подойдёт любое хранилище, совместимое с S3: Yandex Object Storage, Selectel,
VK Cloud. Ниже — Yandex Object Storage: данные остаются в России, платишь за
занятое место (тарифы — на сайте Yandex Cloud). Нужен аккаунт Yandex Cloud с
платёжным аккаунтом (привязанной картой). Хранилище — ещё одно место, где
лежат данные пользователей (пусть и зашифрованные): упомяни его в Политике
обработки данных (docs/LAUNCH_CHECKLIST.md, раздел 2).

**1. Бакет.** В [консоли Yandex Cloud](https://console.yandex.cloud) —
«Object Storage» → «Создать бакет»:

- имя — например `delo-backups-2026`: строчные латинские буквы, цифры и
  дефис; имена общие для всех клиентов, занятое не подойдёт;
- доступ (к объектам, к списку объектов, к настройкам) — «Ограниченный», не
  публичный;
- класс хранилища — «Стандартное».

**2. Ключ доступа.** «Identity and Access Management» → «Сервисные аккаунты»
→ «Создать сервисный аккаунт»: имя `delo-backup`, роль `storage.editor`.
Открой созданный аккаунт → «Создать новый ключ» → «Создать статический ключ
доступа». Консоль покажет идентификатор ключа и секретный ключ. Секретный
показывается **один раз** — не закрывай окно до конца шага 3.

**3. Подключить** — на сервере:

```bash
cd /opt/delo-marketplace
bash scripts/offsite.sh --setup
```

Скрипт спросит хранилище (`1` — Yandex), имя бакета, идентификатор и
секретный ключ (ввод скрыт) и проверит доступ пробным файлом: запись, чтение,
список, удаление. С неверным ключом настройки не сохранятся. Потом спросит
фразу шифрования: нажми Enter — скрипт создаст надёжную, покажет её **один
раз** и попросит подтвердить, что сохранил (`да`). После этого сразу выгрузит
последнюю копию.

> **Фразу — сразу в менеджер паролей** (или на бумагу), но не на этот сервер.
> Если сервер пропадёт, копию из хранилища расшифрует только она: ни Yandex,
> ни разработчик её не восстановят. Ключ от бакета можно выпустить новый,
> фразу — нет.

| Задача | Команда |
|---|---|
| Что лежит в хранилище, итог последней выгрузки | `bash scripts/offsite.sh --list` |
| Выгрузить последнюю копию сейчас | `bash scripts/offsite.sh` |
| Проверить доступ к хранилищу | `bash scripts/offsite.sh --test` |
| Скачать копию на сервер и проверить | `bash scripts/offsite.sh --get ИМЯ` (`latest` — последнюю) |

Скачанная копия ложится в `/var/backups/delo/` рядом с обычными, дальше —
как всегда: `bash scripts/restore.sh ИМЯ`. Как поднять сайт на новом сервере,
если старого нет, — «Сервер пропал: восстановление из облака».

> **Надёжнее** — роль `storage.uploader` вместо `storage.editor`: ключ сможет
> записывать и читать, но не удалять, и взломщик сервера не сотрёт копии в
> хранилище. Старые копии тогда удаляет правило бакета: «Жизненный цикл» →
> удаление объектов через 30 дней. Скрипт сам заметит, что удалять ключу
> нельзя, и удалять не будет (`BACKUP_OFFSITE_KEEP_DAYS=0` в `.env`).

### Скачать копию к себе

Без выгрузки в облако (раздел выше) раз в неделю скачивай свежую копию к себе:
иначе с сервером пропадут и копии. С выгрузкой — по желанию: копия на своём
компьютере не зависит ни от сервера, ни от хранилища. В **Windows cmd** (не в
SSH):

```bat
mkdir C:\delo-backup
scp -r root@213.21.229.145:/var/backups/delo/2026-11-02_003000 C:\delo-backup\
```

Имя — из `bash scripts/backup.sh --list`.

> В копии лежит `.env`: пароли, токены ЮMoney и бота, `SECRET_KEY`. Храни
> папку как пароли и никому не пересылай. `SECRET_KEY` нужен и самой базе: им
> зашифрованы номера документов пользователей — без него их не прочитать.

## Восстановление из копии

```bash
cd /opt/delo-marketplace
bash scripts/restore.sh                    # список копий
bash scripts/restore.sh 2026-11-02_003000  # база и файлы
bash scripts/restore.sh latest             # из последней копии
bash scripts/restore.sh ИМЯ --db-only      # только база
```

Скрипт покажет, что в копии и когда она снята, и попросит ввести `yes`.
Дальше он:

1. проверяет копию: контрольные суммы, оглавление дампа, версию схемы;
2. снимает копию текущего состояния с меткой `pre-restore` — восстановил не
   то, вернёшься к ней этой же командой;
3. останавливает backend, воркер, планировщик и бота — сайт на это время
   отвечает ошибкой;
4. разворачивает копию во временную базу и только потом подменяет рабочую
   (файлы — так же);
5. накатывает миграции до версии кода, запускает сайт, проверяет `/health`.
   Не поднялось — возвращает базу и файлы как было.

`.env` из копии **не восстанавливается** — он лежит в копии на случай переезда
(раздел ниже). Если копия снята более новой версией кода, скрипт откажется и
подскажет, на какую версию сначала перейти.

## Переезд на другой сервер

1. На старом сервере — свежая копия; скачай её к себе (раздел «Резервные
   копии»):

   ```bash
   bash scripts/backup.sh
   ```

2. На новом сервере — код и каталог для копий:

   ```bash
   apt-get update && apt-get install -y git
   git clone https://github.com/topleki57tuu-glitch/delo-marketplace.git /opt/delo-marketplace
   mkdir -p /var/backups/delo
   ```

3. Из Windows cmd — копию на новый сервер:

   ```bat
   scp -r C:\delo-backup\2026-11-02_003000 root@НОВЫЙ_IP:/var/backups/delo/

   ```

он продолжит выгружать свои копии в тот же бакет.

### Сервер пропал: восстановление из облака

Старого сервера нет (или к нему не попасть), а выгрузка в облако была
настроена. Понадобятся ключ от бакета — прежний или новый (раздел «Копии вне
сервера», шаг 2) — и **прежняя фраза шифрования**.

1. На новом сервере — код:

   ```bash
   apt-get update && apt-get install -y git python3 openssl
   git clone https://github.com/topleki57tuu-glitch/delo-marketplace.git /opt/delo-marketplace
   cd /opt/delo-marketplace
   ```

2. Подключить хранилище:

   ```bash
   bash scripts/offsite.sh --setup
   ```

   На вопрос «Это новый сервер, и вы восстанавливаете копию из хранилища?» —
   `y`. Хранилище и бакет — прежние, фраза — **прежняя**: новая старые копии
   не расшифрует.

3. Скачать последнюю копию:

   ```bash
   bash scripts/offsite.sh --get latest
   ```

   Скрипт сверит контрольную сумму, расшифрует копию, проверит файлы и
   положит её в `/var/backups/delo/`. Сайт здесь ещё не установлен, поэтому

   конце напечатает имя копии — оно нужно в шаге 5.

4. Установка:

   ```bash
   bash scripts/vps_deploy.sh
   ```

   На вопрос про демо-данные — «нет».

5. Данные — по **имени** из шага 3, не `latest`: если при установке включил
   копии, она уже сняла копию пустой базы, и `latest` — это она.

   ```bash
   bash scripts/restore.sh 2026-11-02_003000
   ```

6. Свежая копия восстановленного сайта — она же уйдёт в хранилище:

   ```bash
   bash scripts/backup.sh
   ```

7. DNS и bat-файлы — шаги 6 и 7 из «Переезда» выше.

Мониторинг работает на самом сервере: выключится сервер целиком или пропадёт

### Ошибки приложения: Sentry (необязательно)

Мониторинг видит, что сайт лежит, но не видит ошибок внутри работающего
сайта: упавший запрос, сбой фоновой задачи. Для них — Sentry (sentry.io,
есть бесплатный тариф). В `.env` на сервере:

```bash
cp .env .env.bak.$(date +%s)
cat >> .env <<'EOF'
SENTRY_DSN=https://ключ@o123456.ingest.sentry.io/987654
SENTRY_ENVIRONMENT=production
EOF
docker compose -f docker-compose.prod.yml up -d backend worker beat
```

Проверить, что события доходят:

```bash
docker compose -f docker-compose.prod.yml exec backend python -c \
  "import sentry_sdk; from app.core.error_tracking import init_sentry; init_sentry('backend'); sentry_sdk.capture_message('ДЕЛО: проверка Sentry'); sentry_sdk.flush()"
```

Что уходит в Sentry: текст ошибки, стек вызовов, адрес запроса без значений
параметров, имя фоновой задачи, где упало (backend, worker, beat). Что **не**
уходит: IP-адреса, cookies, заголовки (включая токены входа), тела запросов
(паспортные данные, реквизиты, переписка), аргументы задач (адреса и ссылки
из писем), значения переменных, почта и токены из текста ошибок. Настройки и
тест — `backend/app/core/error_tracking.py`,
`tests/security/check_sentry_privacy.py`.

> Sentry — зарубежный сервис. Персональных данных в событиях нет, но решение
> о его использовании оцени с учётом 152-ФЗ. Альтернатива — GlitchTip: он
> принимает тот же `SENTRY_DSN` и ставится на свой сервер.

## Почта (SMTP) и подтверждение адреса

Сайт шлёт два письма: ссылку для сброса пароля и ссылку для подтверждения
адреса после регистрации. Пока почта не настроена, писем нет, а подтверждение
адреса выключено.

**Настроить.** Нужен ящик, от которого пойдут письма (Яндекс Почта, Яндекс 360
для своего домена, Mail.ru), и его **пароль приложения** — не обычный пароль
от ящика. У Яндекса: Яндекс ID → «Безопасность» → «Пароли приложений» →
«Почта». На сервере:

```bash
cd /opt/delo-marketplace
cp .env .env.bak.$(date +%s)
grep '^SMTP_' .env   # строки уже есть? Тогда поправь их в nano .env, а не дописывай
cat >> .env <<'EOF'
SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_USER=ящик@yandex.ru
SMTP_PASS=пароль_приложения
SMTP_FROM=ящик@yandex.ru
EOF
docker compose -f docker-compose.prod.yml up -d
```

`SMTP_FROM` — тот же адрес, что `SMTP_USER`: чужой адрес отправителя Яндекс не
пропустит. Порт 465 — шифрование сразу; если хостинг его закрыл — 587.

**Проверить** — тестовое письмо себе:

```bash
docker compose -f docker-compose.prod.yml exec backend python -m app.core.email --test твой@адрес
```

«Письмо отправлено» — всё готово (во «Входящих» нет — загляни в «Спам»).
Иначе команда напишет причину: неверный пароль, не тот адрес отправителя,
закрытый порт. Яндекс не принимает пароль приложения — проверь в настройках
Яндекс Почты → «Почтовые программы», что доступ почтовым программам разрешён.

**Как работает подтверждение**, когда почта настроена:

- после регистрации приходит письмо со ссылкой, она действует 3 дня;
- пока адрес не подтверждён, под шапкой сайта висит полоска «Подтвердите
  почту» с кнопкой «Отправить письмо ещё раз» — не чаще трёх писем в час;
- **вывод денег** — только с подтверждённым адресом: по почте
  восстанавливается пароль, и выводить деньги должен владелец ящика, а не
  тот, кто вписал чужой адрес;
- аккаунты, созданные до настройки почты, тоже считаются неподтверждёнными:
  их владельцы увидят полоску, нажмут «Отправить письмо ещё раз» и перейдут
  по ссылке из письма;
- в админ-панели у таких пользователей отметка «почта не подтверждена».

Снять требование для вывода (письма и полоска останутся) —
`EMAIL_VERIFICATION_REQUIRED=0` в `.env` и
`docker compose -f docker-compose.prod.yml up -d`.

## Что НЕ надо делать

- **Не запускать `vps_deploy.sh`** на работающем сервере. Он для первой
  установки: перезапишет `.env` и сменит пароль БД.
- **Не использовать старые инструкции из `docs/archive/`: `legacy/deploy-manual.txt`,
  `legacy/nginx-delomaster.conf`, `DOMAIN_SETUP_delomaster_online.md`.** Это старая дорога под домен
  `delomaster.online` и IP `92.53.96.169`. Конфликтует с Caddy за порты 80/443.
- **Не править `.env` без бэкапа.** `cp .env .env.bak.$(date +%s)` перед любой
  правкой — секунда работы.
- **Не менять `SECRET_KEY` в `.env`.** Им зашифрованы номера документов
  пользователей в базе: с новым ключом их не прочитать — ни в базе, ни в
  резервных копиях.
- **Не удалять `/var/backups/delo` и `/var/lib/delo`** ради места. Там
  резервные копии и журнал обновлений, по которому работает `--rollback`.
  Место освобождает `docker system prune -af`, а старые копии удаляются сами.
- **Не пересылать скачанные копии.** В каждой — `.env` со всеми паролями и
  токенами.
- **Не менять и не терять фразу шифрования копий**
  (`BACKUP_ENCRYPTION_PASSPHRASE`). Копии в облаке расшифровываются только
  ею, а хранится она в `.env` — то есть пропадёт вместе с сервером, если её
  нет ещё и в менеджере паролей.
- **Не удалять `deploy/Caddyfile` на сервере.** В git лежат только
  `deploy/Caddyfile.domain` и `deploy/Caddyfile.http`; сам `deploy/Caddyfile`
  создаётся при первой установке и **не отслеживается** — поэтому
  `git reset --hard` его не трогает, и правки в нём переживают обновление.
  Caddy смонтирован именно на этот файл: удалишь — стек не поднимется.
- **Не писать домен кириллицей** в `DOMAIN`, `FRONTEND_URL`, `CORS_ORIGINS`.
  Только punycode `xn--d1acsm.online`: Caddy не принимает юникод в адресе
  сайта, Let's Encrypt выдаёт сертификаты только на ASCII, а браузер шлёт
  punycode в `Origin`, из-за чего CORS не совпадёт.

**Работает:** домен, HTTPS (Let's Encrypt), SPA, backend, postgres, Redis,
Caddy, бот (контейнер поднят). ЮMoney подключён: `/payments/status` отдаёт

### Сначала это: вебхук ЮMoney

**Проверь адрес уведомлений в кабинете ЮMoney.** Он настраивается отдельно
от кода, и пока там указан старый домен, уведомления об оплате не приходят
вообще: приложение не получает ни ошибки, ни записи в логе — только
пользователь с деньгами, ушедшими со счёта, и непополненным балансом.
Именно так и потерялось первое пополнение на 100 ₽.

Адрес должен быть ровно такой:

```
https://xn--d1acsm.online/payments/webhook/yoomoney
```

`YOOMONEY_NOTIFICATION_SECRET` в `.env` на сервере и секрет в кабинете
ЮMoney должны совпадать — иначе вебхук отвечает `403 Invalid signature`,
и это **видно в логах**, в отличие от неверного адреса.

#### Настроить, клик за кликом

Страница настроек (официальная документация:
<https://yoomoney.ru/document/http-uvedomleniya>):

```
https://yoomoney.ru/transfer/myservices/http-notification
```

1. Войти в тот кошелёк, **на который принимаешь деньги** — уведомления
   настраиваются на кошелёк, а не на приложение.
2. Поставить галочку **«Отправлять HTTP-уведомления»**. Без неё адрес
   сохранится, но отправлять ничего не будут.
3. В поле адреса вписать ровно:
   `https://xn--d1acsm.online/payments/webhook/yoomoney`
4. Нажать **«Показать секрет»** и скопировать секретное слово.
5. Сверить его с сервером:

```bash
grep YOOMONEY_NOTIFICATION_SECRET /opt/delo-marketplace/.env
```

Не совпало — привести к одному значению и перезапустить backend:

```bash
docker compose -f docker-compose.prod.yml up -d backend
```

6. Сохранить.

**Адрес может быть только один.** Все входящие переводы на этот кошелёк
пойдут на него — не только пополнения из приложения. Наш вебхук отбивает
чужие метки с `404 Unknown payment label` и пишет это в лог; это нормально.

#### Проверить, что доходит

На странице настроек есть кнопка **«Протестировать»**. Нажми её, а потом
сразу смотри логи сервера:

```bash
cd /opt/delo-marketplace
docker compose -f docker-compose.prod.yml logs --tail 100 backend | grep -i yoomoney
```

**Ожидаемый результат — ошибка, и это правильно.** Тестовое уведомление
приходит **пустым**, без подписи, и наш вебхук его отклоняет: в логе
появится `Invalid ЮMoney webhook signature: {...}`. Признак исправного
адреса — что строка вообще появилась: значит запрос дошёл.

| Что в логе | Что это значит |
|---|---|
| `Invalid ЮMoney webhook signature` | Адрес верный. Либо это тестовое пустое уведомление, либо секрет не совпадает |
| Пусто | Адрес всё ещё неверный или сервер недоступен |
| `credited: N RUB to user` | Всё работает, деньги зачисляются |

**Тестовая кнопка деньги не зачисляет** — тестовое уведомление пустое.
Настоящая проверка только одна: пополнить на 100 ₽ и через минуту увидеть
`ЮMoney payment delo_... credited: 100 RUB to user ...` и выросший баланс.

#### Важно про способ оплаты

ЮMoney присылает уведомления только когда кошелёк пополнили **через их
виджет или кнопку** — с карты или из другого кошелька. Приложение
использует именно форму `quickpay`, так что случай наш. Но если деньги
пришли каким-то другим способом, уведомления не будет **по определению**, и
спасает только кнопка восстановления в профиле.

#### Если платёж всё-таки потерялся

У пользователя в профиле есть кнопка «Оплатил, но баланс не изменился» —
она дозачисляет платежи, которые провайдер провёл, а мы не увидели.
Ручной путь, если понадобится:

```bash
docker compose -f docker-compose.prod.yml exec postgres \
  psql -U marketplace -d marketplace_db -c \
  "SELECT id, payment_id, user_id, amount, status, credited_at, created_at
   FROM payment_records ORDER BY id DESC LIMIT 10;"
```

Строка с `credited_at = NULL` и оплаченная у провайдера — это и есть
потерянное пополнение.

### Остальное, требуется вручную

- **`TELEGRAM_BOT_TOKEN`** — пустой, бот не функционирует.
- **Вход в админ-панель** — `bash scripts/admin_access.sh` из
  `/opt/delo-marketplace`. Спросит почту и пароль (ввод скрыт), заведёт
  аккаунт или сменит ему пароль, впишет почту в `ADMIN_EMAILS` и перезапустит
  backend. `--check` — кто сейчас модератор и нет ли «двойников» вроде
  `Admin@delo.ru`. С сайта адреса модераторов не регистрируются.

- **`YOOMONEY_CLIENT_ID`** — нужен только для OAuth-сценария. Коду
  `client_secret` **не нужен** — он нигде не читается.
- **Резервные копии** — пока не включены: `bash scripts/backup.sh --install`
  (раздел «Резервные копии»), потом выгрузка в облако:
  `bash scripts/offsite.sh --setup` (раздел «Копии вне сервера»).
- **Почта (SMTP)** — если ещё не настроена: без неё не уходят письма сброса
  пароля и подтверждения адреса (раздел «Почта (SMTP) и подтверждение
  адреса»).
- **Уведомления о сбоях** — `bash scripts/monitor.sh --setup` и внешняя
  проверка в UptimeRobot (раздел «Мониторинг и уведомления»).
